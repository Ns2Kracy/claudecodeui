# 远程 OAuth 回调与账户局部加载设计

## 问题

CloudCLI 部署在 ZimaOS 等远程主机时，Codex/OpenAI OAuth 仍使用固定的 `http://localhost:1455/auth/callback`。授权页面中的 `localhost` 指向用户浏览器所在设备，而不是 NAS，因此自动回调可能无法到达 CloudCLI。与此同时，添加供应商后的账户和模型刷新会把已有账户区域整体替换成加载卡片，导致不必要的页面闪烁和上下文丢失。

## 方案

### OAuth 自动回调与手动兜底

保留现有 `localhost:1455` 自动回调监听。OAuth 对话框同时提供“无法自动完成？”的折叠区域，允许用户粘贴浏览器最终停留的完整回调地址。

前端只接受 `http://localhost:1455/auth/callback`（兼容 `127.0.0.1`）且必须包含 OAuth `code`；上游 `error` 参数转换为安全、可重试的提示。前端复用当前 OAuth 完成 API，不记录或回显 code/state。提交成功后关闭对话框并后台刷新账户和模型。

### 局部加载

账户和模型首次尚无数据时仍显示初始加载卡片。已有数据后的刷新保持当前内容可见，通过局部 `aria-busy` 状态和当前操作按钮 spinner 表示后台工作。

创建、OAuth 连接、更新、测试和删除只禁用当前相关控件。后台刷新失败保留旧数据，并在账户区域显示可重试的小型错误提示，不清空整个账户页面。

## 错误与安全

- 拒绝非 localhost、错误端口、错误路径、缺少 code 的手动回调地址。
- OAuth `error` 映射为一般错误，不在 UI 或日志中泄露 code/state。
- 重复提交在当前 OAuth 操作完成前禁用。
- 自动回调与手动回调共享同一事务完成路径，先完成的一方获胜。

## 验证

- 单元测试覆盖合法/非法手动回调解析和上游错误。
- 组件测试覆盖手动粘贴表单、提交状态和自动流程保留。
- 状态与账户组件测试覆盖首次加载、已有数据后台刷新、刷新失败保留内容及局部 mutation loading。
- 运行目标测试、typecheck、lint 和 build，并在浏览器中验证远程部署交互。
